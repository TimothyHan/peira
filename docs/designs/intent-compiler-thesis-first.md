## Problem Statement

API test suites can't be trusted at the speed AI now writes them. Every "AI-native" testing tool ships AI as an operator over legacy artifacts (generated Playwright code, self-healing selectors) — a human still can't tell, without reading generated code, whether the suite asserts what the team means. Rikki-Tikki inverts the design: human-owned acceptance criteria and invariants (markdown) compile via LLM at authoring time into schema-gated declarative JSON cases run by a deterministic, zero-LLM runner. The full design is RFC 0001 (`docs/DESIGN.md` in the repo), already desk-audited against a 27-case ground-truth corpus from the author's 2022 framework.

## What Makes This Cool

- **The oracle wall is structural, not conventional.** Generated code may implement procedure; the JSON Schema refuses any case whose assertion isn't declarative data. A model can argue with a prompt; it can't argue with a validator.
- **The DSL has a fossil record.** Every escape-to-code emission is logged as telemetry; recurring shapes get promoted into primitives *with evidence*, then migrated back to declarative. No test DSL has ever had a paper trail for why its features exist.
- **Failures get adjudicated, never absorbed.** Triage classifies each failure as bug, drift, or flake (RFC §4.7 taxonomy) and proposes intent-level diffs a human approves; nothing self-heals silently. The bug demo is real: the author's own 2022 suite encoded observed 401 where intent said 403, silently — found by pre-registered audit before a line of code was written.

## Constraints

- Zero-dependency Node ≥ 18 (family convention with Akela). LLM access for `compile`/`triage` uses native `fetch` against a configurable provider endpoint (default: the Claude API); both run on recorded artifacts between runs, never during one.
- No LLM at runtime, ever — compile and triage only, both proposal-gated.
- v1 is functional API testing of live RESTful services; UI, load, contract-brokering, traffic capture are non-goals (RFC §6).

## Premises (agreed 2026-08-27)

1. **First user is the author** — v1 must serve a solo QA engineer testing a RESTful service before it's a platform.
2. **The differentiator is trust discipline, not generation speed** — competing on the synthesis (oracle wall + telemetry + triage), not the ingredients.
3. **Distribution is scope, not an afterthought:** public GitHub repo + npm + CI running the in-repo fixture bed green. The ported 2022 cases and the triage demo are the demo. Publishing is gated on the naming decision (see Open Questions); `rikki-tikki` was verified free on npm 2026-08-27.
4. **Akela stays decoupled** until both engines stabilize (RFC §4.8); the runner writes a flat JSONL **evidence log** (runs, verdicts, triage decisions) for v1. Escape-hatch telemetry (§4.6) is a separate stream that begins when code steps exist.

## Cross-Model Perspective (adopted decisions only)

An independent cold read (fresh-context subagent, structured summary only) shaped two decisions and one deferred trajectory:

- **Adopted — build order:** do not start with the compiler; it's the commodity part and hand-written JSON is a fine compiler stub. Build the schema wall, the planted-failure fixture, the evidence log, and minimal triage first. (This is Approach B below.)
- **Adopted — fixture design:** plant a deterministic flaky endpoint so triage demos the flake verdict, not just bug/drift.
- **Deferred — the drift observatory:** point the tool at third-party APIs (Stripe, GitHub) with public intent files on cron, publishing intent-level diffs when vendor behavior changes. Only a non-self-healing architecture can do this. Not v1 (conflicts with Premise 1; can't inject deliberate shifts into someone else's API); recorded as the strongest known phase-2 trajectory and distribution story.

## Approaches Considered

### Approach A: Corpus-first (RFC 0001 §7 as originally written)
PR1 = full schema + runner + all 27 ported cases green, then compiler, telemetry, triage. Low risk, but the three novel mechanisms arrive last; the repo demos the ancestor's ground before the new idea. Not chosen.

### Approach B: Thesis-first vertical slice (chosen)
Schema v0 (including the step schema, so refusal fixtures exist) → runner + fixture service with three planted behaviors → minimal intent layer + 3 ported cases + evidence log from commit one → minimal `triage` nailing all three verdicts. Compiler stays a hand-written stub; corpus completion and the compiler follow.

### Approach C: Observatory-first
Aim v1 at a real third-party API with public intent files and cron-published drift diffs. Rejected for v1 in-session: kills the triage-precision measurement (can't inject shifts), violates Premise 1. Recorded as phase-2 trajectory.

## Recommended Approach

**B.** It front-loads proof of the only claims that are novel; the README demo (a failure adjudicated and proposed as an intent edit instead of silently healed) *is* the pitch. The cost B pays — corpus completion moves later — was already paid down by the 2026-08-27 desk audit that verified all 27 cases are expressible in the day-one DSL (RFC §4.3). ## The Fixture's Three Planted Behaviors

Plants are **isolated behind a fixture mode flag** (`--plant bug,drift,flake`); with no flag the fixture is intent-faithful and clean. PR2's triage demo runs with plants on; PR3's 27-case all-green gate runs plants off; PR6's deliberate-shift injection reuses the same plant mechanism. Plants never poison the corpus surface.

1. **Bug:** with the plant on, the status endpoint returns 401 for cross-user access where intent says 403 — behavior contradicts intent (RFC §4.7: bug). Triage emits a structured finding, not an intent diff. The ported case is **authored from intent (expects 403)**, deliberately diverging from the 2022 spec's observed-401 assertion; PR4's compile-time adjudication later re-derives that divergence mechanically.
2. **Drift:** with the plant on, the submit endpoint returns 202 where the intent section says "accepted" and the case (written when intent was) expects 200 — behavior still satisfies intent (RFC §4.7: drift). Triage proposes the intent-level clarification plus the recompiled case — in PR2 that "recompile" is hand-authored compiler-stub output matching the proposed diff; PR4 replaces it with a real recompile.
3. **Flake:** one endpoint fails deterministically every 3rd request via an internal counter — reproducible by construction (RFC invariant 8 holds; verdicts remain a function of cases, seed, and service state). Triage's prescription "re-run by seed" is meaningful because the flakiness is counter-based, not random.

## Success Criteria

- Schema v0 refuses the right things in CI: an assertion smuggled into a code step, and a case without `from: {intent, hash}` provenance, both fail validation with fixture files proving it.
- The thesis slice runs green (and correctly red) against the fixture: 3 ported cases; triage emits **bug + structured finding** for the 401/403 plant, **drift + intent diff** for the 202 plant, and **flake + re-run prescription** for the counter plant.
- All 27 ported 2022 cases green with zero escape hatches and zero sleeps (PR3 gate).
- Compile fidelity measured against the 2022 test plan (agreement rate, refusals, adjudications) once the compiler lands (PR4 gate).
- Public repo + npm publish + CI green — distribution shipped, not deferred (PR6, name-gated).

## Distribution Plan

- GitHub Actions CI: runs the in-repo fixture service + full case suite + schema-refusal fixtures on push.
- README leads with the triage demo recording (a failure adjudicated into an intent edit), not feature lists.
