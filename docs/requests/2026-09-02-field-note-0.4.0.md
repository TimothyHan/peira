# Field note: `$absent` found two security bugs on its first day

**For:** TimothyHan/peira · **From:** the consumer behind RFC 0002 and the 0.3.0 field report
(BusinessIndex multi-tenant platform on Payload CMS) · **Peira version:** 0.4.0, one release
after [the field report](2026-09-02-field-report-0.3.0.md) that proposed the matcher.

I rewrote the `/api/access` case with the new matcher — `"artists": {"$absent": true}`,
`"tenants": {"create": {"$absent": true}}` — expecting it to pass, since the positive-form case
already did. It failed on both keys. Two HTTP cases later:

- `GET /api/artists/versions` as an editor of a different tenant → 200, drafts included.
- `POST /api/tenants` as that editor → 201.

Both real, both fixed within the hour, both now pinned in the suite. Neither was caught by 140
in-process tests with access control on, and I think the reason is worth stating in your docs:
those tests all asked "can this user read what they should?" The `$absent` case asked "what
does this user hold that they shouldn't?" — a negative claim over the whole permission map —
and that question had simply never been posed. The matcher didn't just make an existing claim
tidier; it made a new kind of claim writable.

Two small things that made this fast, credit where due: `validate` refused my first
`$contains` misuse with the fix in the message, and `stamp --check` meant I could restamp the
intent section after editing it and get back to running in seconds, no model in the loop.

Suggestion, low cost: put this shape in the `$absent` docs as the motivating example — "an
access map that omits denied permissions; assert the omissions, not the grants". It's the case
that shows why the matcher exists, and it's the case most multi-tenant APIs have.

On the declined nonce: agreed, on reflection. A fresh seed per local run was the right answer;
the docs now say so, and the collision hasn't recurred.

Thanks for turning the report around in a day.
